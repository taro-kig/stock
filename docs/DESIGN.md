# AI 中期株トレーディングシステム 設計書 (v0.1)

## 0. この文書について

- 対象: 数週間〜数ヶ月の保有を前提とした **中期売買** システム
- 制約: **安価な LLM (Gemini Flash / Flash-Lite 級など) の組み合わせ** で成立させる
- 目標: 安いモデルの弱点 (幻覚・ブレ・形式崩れ) を **ハーネス (検証の仕組み)** で補い、低コストで高い信頼性を得る
- 本書は投資助言ではない。実資金投入は段階的な検証 (§10) を通過してから行う

---

## 1. 設計原則

| # | 原則 | 理由 |
|---|------|------|
| P1 | **LLM に売買を決めさせない** | LLM は「文章 → 構造化データ」の変換器として使う。売買判断・資金配分・損切りは決定論的なルールで行う。再現性があり、バックテストでき、暴走しない |
| P2 | **中期なので日次バッチで十分** | リアルタイム処理が不要 → ストリーミング基盤も高速モデルも不要。コストが桁で下がる |
| P3 | **安いモデルは「数」と「検証」で補う** | 1回の高価なモデル呼び出しより、異なる系統の安いモデル2〜3個 + 機械的検証の方が安く・誤りに強い |
| P4 | **LLM を使う前に、使わずに済ませる** | 重複除去・銘柄辞書マッチ・キーワード判定で 7〜9 割の文書は LLM に渡さず捨てられる |
| P5 | **迷ったら何もしない (fail-safe)** | データ欠損・モデル不一致・予算超過・異常値のときは「新規エントリーしない」に倒す |
| P6 | **すべてを記録し、後で答え合わせする** | 全シグナルとその後のリターンを保存し、モデル・情報源ごとの当たり率を測って重みを更新する |

                       │                                         │                                    │
                       │                                         ▼                                    │
                       │  ⑥ スコアリング → ⑦ ポートフォリオ構築 → ⑧ リスクチェック (決定論的)         │
                       │                                         │                                    │
                       └─────────────────────────────────────────┼────────────────────────────────────┘
                                                                 ▼

                                                                 │

### 実行頻度

| 処理 | 頻度 | 備考 |
|------|------|------|
| 情報収集 + LLM 抽出 | 1日1〜3回 | 引け後に1回で十分。決算シーズンは増やしてもよい |
| ストップ/イベント監視 | 1日1回 | 損切り・重大な悪材料による撤退 |
| リバランス (新規/入替) | 週1回 | 中期なので回転を抑える。売買コスト・税コストを削減 |
| 評価・重み更新 | 月1回 | 答え合わせデータが溜まってから |

## 3. データソース

「複数のサイトから集める」の中身。**公式 API・RSS を優先** し、スクレイピングは各サイトの利用規約・robots.txt を確認したうえで最小限に留める。

| 種類 | 日本株 | 米国株 | コスト | 中期シグナルとしての価値 |
|------|--------|--------|--------|--------------------------|
| 価格・出来高 | J-Quants API, yfinance, stooq | yfinance, Alpaca, stooq | 無料〜少額 | ◎ モメンタム/トレンドの基礎 |
| 財務・業績 | J-Quants (決算短信), EDINET API | SEC EDGAR (XBRL) | 無料〜少額 | ◎ 業績修正・クオリティ |
| 適時開示 | TDnet (適時開示情報閲覧サービス) | SEC 8-K | 無料 | ◎ 上方修正・自社株買い・M&A 等の一次情報 |
| ニュース | Google News RSS, 各社 RSS, かぶたん等 | Finnhub, Yahoo Finance RSS, 各社 RSS | 無料〜少額 | ○ 一次情報の補強・複数報道による裏取り |
| アナリスト評価 | 各種ニュース経由 | Finnhub 等 | 無料〜少額 | ○ レーティング変更 |
| SNS・掲示板 | (規約上の制約が大きい) | Reddit API 等 | 中〜高 | △ ノイズ大。重みは低く、単独では使わない |
| マクロ | 日銀, e-Stat | FRED, VIX | 無料 | ○ 地合い判定 (レジームフィルタ) |

### 情報源の信頼度

- 情報源ごとに **信頼度の重み** を持つ (初期値は手動: 一次開示 > 大手報道 > まとめ系 > SNS)
- 運用データが溜まったら、情報源ごとの「抽出イベントの方向 × その後20営業日の超過リターン」の当たり率で **ベイズ更新 (Beta 分布)** する
- **裏取り (corroboration)**: 同一イベントが独立した 2 つ以上の情報源で確認されたら重みを上げる。SNS 単独の噂は加点しない

## 4. シグナル設計

中期で実績のある (学術的にも知られた) 効果を土台にし、LLM は「文章でしか取れない情報」に限定して使う。

### 4.1 定量ファクター (LLM 不要)

| ファクター | 定義例 | 中期での意味 |
|-----------|--------|--------------|
| モメンタム 12-1 | 直近1ヶ月を除く過去12ヶ月リターン | 中期トレンド継続 |
| トレンド | 終値 > SMA200 かつ SMA50 > SMA200 | 下落トレンド銘柄を避ける |
| 相対強度 | 対指数 (TOPIX / S&P500) の 3〜6ヶ月超過リターン | 強い銘柄に乗る |
| ボラティリティ | 60日実現ボラ, ATR | ポジションサイズ・損切り幅に使用 |
| 業績修正 | 会社予想・コンセンサスの上方/下方修正 | 決算後ドリフト (PEAD) |
| クオリティ/バリュー | ROE, 営業利益率, PER/PBR 等 | 補助的に |

### 4.2 LLM 由来のイベントシグナル

LLM の役割は **ニュース・開示 1 件を以下の構造化データに変換すること「だけ」** (スキーマは `src/stockai/signals/models.py`)。

```json
{
  "relevant": true,
  "tickers": ["7203"],
  "event_type": "guidance_up",
  "direction": 2,          // -2〜+2 : 株価への影響方向と強さ
  "materiality": 3,        // 0〜3   : 重要度
  "horizon": "months",     // days / weeks / months
  "confidence": 0.8,
  "evidence": ["通期の営業利益予想を従来の4.3兆円から4.9兆円に上方修正"],
  "rationale": "通期ガイダンスの大幅上方修正"
}
```

イベント種別は列挙型に固定 (自由記述させない)。日本固有の事象 (上方修正, 公募増資, MSワラント等) もここにマップする。

### 4.3 イベントスコアの集約

銘柄 i の日次イベントスコア:

```
event_score_i = Σ_e  direction_e × w_materiality(e) × confidence_e × w_source(e) × exp(-age_e / half_life)
                × (1 + corroboration_bonus  if 独立情報源 ≥ 2)
```

- half_life は horizon に応じて変える (days: 3日, weeks: 10日, months: 30日)
- 最終的には他のファクターと同様に、ユニバース内で z スコア化して合成する

## 5. LLM ハーネス (本システムの中核)

安いモデルを「信頼できる部品」にするための仕組み。実装は `src/stockai/harness/`。

### 5.1 コストの階層 (カスケード)

```
Tier 0  ルール       : 重複除去, 銘柄辞書マッチ, 既処理キャッシュ           コスト 0
Tier 1  安価モデル   : Flash-Lite 級 × 2〜3 系統 (Gemini + 他社の安価モデル)   ほぼ全件
Tier 2  中位モデル   : Flash / Pro 級 — Tier1 が割れた かつ 重要な案件のみ     全体の数%
(Tier 3 人間         : 発注直前の承認。初期フェーズでは必須)
```

**昇格条件 (Tier1 → Tier2)**: 「Tier1 で合意が取れない」かつ「保有銘柄 or 上位候補 or materiality ≥ 2」。重要でないものは合意が取れなければ **シグナル無し (= 0) として捨てる** (P5)。

### 5.2 信頼性を担保する 6 つの仕組み

| # | 仕組み | 何を防ぐか | 実装 |
|---|--------|-----------|------|
| H1 | **構造化出力 + スキーマ検証 + 再試行** | 形式崩れ・範囲外の値 | JSON モード + Pydantic 検証。失敗時はエラー内容を添えて再試行 (最大 N 回) |
| H2 | **根拠の機械検証 (grounding)** | 幻覚 | モデルに原文からの引用を必須とし、**引用が原文に実在するか文字列照合**。実在しなければ棄却。ティッカーも「事前フィルタで渡した候補」以外は棄却 |
| H3 | **異系統アンサンブル + 多数決** | 単一モデルの癖・ブレ | 別ベンダーのモデルで同じ抽出を行い、(イベント種別, 方向の符号) で投票。合意率を信頼度に反映 |
| H4 | **コンテンツハッシュ・キャッシュ** | 重複コスト | (モデル, プロンプト版, 入力) のハッシュで結果を保存。同じ記事は二度と課金しない |
| H5 | **予算ガード** | コスト暴走 | 日次の上限額を超えたら LLM 呼び出しを停止 (= その日はシグナル無し) |
| H6 | **評価とキャリブレーション** | 気づかない劣化 | ゴールデンセット (人手ラベル付き 100〜300 件) で、プロンプト/モデル変更時に回帰テスト。運用データでモデル別・情報源別の当たり率を追跡 |

### 5.3 なぜ「異系統」なのか

同じモデルを温度を変えて複数回呼ぶ (self-consistency) より、**別ベンダーのモデルを組み合わせる** 方が誤りの相関が低く、多数決の効果が大きい。例:

- Gemini Flash-Lite 級 (Google)
- DeepSeek / Qwen / GPT-mini 級 など (OpenAI 互換 API や OpenRouter 経由で切替可能に)

モデル名・価格は設定ファイル (`config/config.example.yaml`) で差し替えられるようにし、コードに埋め込まない。

### 5.4 さらにコストを下げる工夫 (後続フェーズ)

- 見出しだけで判定できるものは見出しのみ送る / 短い記事は複数件をまとめて 1 回で送る (バッチ化)
- システムプロンプトを固定してプロンプトキャッシュ (コンテキストキャッシュ) を効かせる
- 当たり率の低いモデル・情報源はアンサンブルから外す

## 6. 意思決定 (決定論的)

### 6.1 ユニバース

- 流動性フィルタ: 平均売買代金が一定以上 (例: 日本株 5 億円/日以上, 米国株 2,000 万ドル/日以上)
- 例: TOPIX500 / S&P500 構成銘柄から開始

### 6.2 スコア合成

```
score_i = Σ_k w_k × clip(zscore(factor_k)_i, -3, 3)
```

初期重み例: モメンタム 0.35 / 業績修正・イベント 0.35 / 相対強度 0.15 / クオリティ 0.15。
重みはバックテストで過剰最適化しないよう **少数のパラメータ・粗いグリッド** でのみ調整する。

### 6.3 エントリー条件 (すべて満たす)

1. スコア上位 N 位以内 (例: N=10)
2. トレンドフィルタ OK (終値 > SMA200)
3. 地合いフィルタ OK (指数 > SMA200。NG の場合は新規エントリー停止 or 半分のサイズ)
4. 直近に重大な悪材料イベントなし
5. 決算発表直前 (例: 3営業日以内) ではない

### 6.4 エグジット条件 (いずれか)

| 種類 | ルール例 |
|------|----------|
| 損切り | 建値 − 2.5 × ATR(20) |
| トレーリング | 高値 − 3 × ATR(20) |
| 順位劣化 | スコア順位が N × 2 位より下 (ヒステリシスで売買回転を抑える) |
| シナリオ崩壊 | materiality ≥ 2 の負のイベントが合意付きで検出 |
| 時間切れ | 60営業日経っても含み益にならない |

### 6.5 ポジションサイズとリスク上限

- 1 トレードのリスク = 口座資産の 0.75% (損切り幅で割って株数を決める)
- 1 銘柄の上限 10%、1 セクター上限 30%、最大保有数 10〜15
- 日本株は **単元株 (100株)** に丸める
- **キルスイッチ**: 口座のドローダウンが −15% で新規停止、−25% で全体を縮小し人間の判断待ち

## 7. 執行

| フェーズ | 方式 |
|---------|------|
| 初期 | **ペーパートレード** (仮想約定。翌日始値 + スリッページで約定させる) |
| 中期 | **承認制**: 発注提案を Slack/Discord/LINE に通知 → 人が承認したものだけ発注 |
| 後期 | 小額・上限付きで自動発注 |

ブローカーはアダプタで抽象化する (`Broker` インターフェース: 残高取得 / 建玉取得 / 発注 / 取消)。
候補 (要確認): 日本株 = kabuステーション API (auカブコム), 立花証券 e支店 API など / 米国株 = Alpaca (ペーパー口座あり), Interactive Brokers。

中期売買なので発注は **寄付の成行 or 指値** で十分。スリッページ・手数料・税をバックテストとペーパーで必ず考慮する。

## 8. データ保存

最初は単一の SQLite (後で DuckDB / PostgreSQL に移行可能な形)。

| テーブル | 内容 |
|---------|------|
| documents | 収集した文書 (URL, 情報源, 取得時刻, 公開時刻, 本文, ハッシュ) |
| extractions | 文書 × モデルごとの抽出結果 (生 JSON, 検証結果, 合意結果) |
| llm_calls | モデル, トークン数, コスト, レイテンシ, キャッシュヒット |
| prices / fundamentals | 日次価格・財務 |
| signals | 日次の銘柄別スコア (point-in-time) |
| orders / positions | 提案・承認・約定・保有 |

**重要: point-in-time 記録。** すべてのデータに「いつ知り得たか (取得時刻)」を持たせ、バックテスト・評価で未来の情報を使わないようにする。

## 9. 検証の落とし穴

| 落とし穴 | 対策 |
|---------|------|
| 先読みバイアス | 取得時刻ベースで結合。開示の公表時刻 (引け後開示は翌日扱い) を厳守 |
| 生存者バイアス | 上場廃止銘柄を含むユニバースで検証 |
| **LLM の知識リーク** | LLM は過去の株価の結末を知っている。過去ニュースに LLM を当てたバックテストは楽観的になる。→ **LLM 由来シグナルの評価は、モデルの学習カットオフ以降のデータ or 今後のフォワードテストで行う**。過去検証では社名・日付の匿名化で緩和 |
| 過剰最適化 | パラメータ数を絞る。ウォークフォワード検証。アウトオブサンプル期間を確保 |
| コスト無視 | 手数料・スリッページ・税を差し引いた成績で判断 |

## 10. ロードマップ

| Phase | 内容 | 合格条件 |
|-------|------|----------|
| **0 (今回)** | 設計書。ハーネス中核 (構造化出力・根拠検証・アンサンブル・キャッシュ・予算)、RSS 収集、テクニカル指標、リスク計算 | テスト通過 |
| 1 | 価格・財務データ取込、定量ファクター、**定量部分のみのバックテスト** | 手数料込みで指数に対し妥当な成績 |
| 2 | 情報収集 + LLM 抽出を毎日実行して蓄積。ゴールデンセット作成。モデル・情報源の評価 | 抽出精度 (人手ラベル比) ≥ 85%、1日コストが予算内 |
| 3 | ペーパートレード (提案 → 通知 → 仮想約定) を **3ヶ月以上** | LLM シグナルあり/なしで比較し、上乗せ効果を確認 |
| 4 | 承認制で少額実運用 → 段階的に自動化 | ドローダウン・乖離が想定内 |

## 11. コスト見積り (目安)

仮定: ウォッチ 100〜500 銘柄、収集 300 件/日 → 重複除去・事前フィルタ後 100 件/日、Tier1 を 2 モデル、1件あたり入力 1,200 / 出力 250 トークン、Tier2 昇格 5%。

- Tier1: 100 件 × 2 モデル × (1,200 + 250) トークン ≈ 入力 24 万 / 出力 5 万 トークン/日
- Flash-Lite 級の単価を 入力 $0.1/100万・出力 $0.4/100万 と仮定すると **約 $0.05/日**
- Tier2 を含めても **月 $2〜5 程度**。10 倍に膨らんでも月数千円

→ **LLM 代はボトルネックにならない。** 支配的なのは有料データ (J-Quants 等) と実行環境の費用。
(単価は変動するので実際の料金ページで確認すること。無料枠は入力が学習に使われる場合がある点に注意)

## 12. 運用・監視

- 毎日のレポート: 収集件数 / LLM 処理件数 / キャッシュヒット率 / 合意率 / 根拠検証の棄却率 / コスト / 提案一覧
- 異常検知: 収集 0 件・合意率の急低下・棄却率の急上昇 → その日は新規エントリーを止めて通知
- プロンプトはバージョン管理し、変更時はゴールデンセットで回帰テストしてから切替

## 13. 法令・規約メモ

- 個人の自己売買目的での利用を想定。シグナルを他人に提供・販売する場合は投資助言・代理業の登録が必要になり得る
- 各サイトの利用規約・API 規約・robots.txt を守る。有料記事の本文を無断取得しない
