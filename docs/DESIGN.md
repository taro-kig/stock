# AI 中期株トレーディングシステム 設計書 (v0.2)

## 0. この文書について

- 対象: 数週間〜数ヶ月の保有を前提とした **中期売買** システム
- 制約: **安価な LLM (Gemini Flash / Flash-Lite 級など) の組み合わせ** で成立させる
- 目標: 安いモデルの弱点 (幻覚・ブレ・形式崩れ) を **ハーネス (機械的な検証の仕組み)** で補い、低コストで高い信頼性を得る
- 実装: **TypeScript (strict) / Node.js 22**。処理は **ワークフロー (ノードのグラフ)** として組む
- 本書は投資助言ではない。実資金投入は段階的な検証 (§11) を通過してから行う

## 1. 設計原則

| # | 原則 | 理由 |
|---|------|------|
| P1 | **「何を・いつ」は AI、「いくら・どこまで損するか」はルール** | AI に売買判断を任せても、サイズ・損切り・上限・キルスイッチは決定論的ルールが握る。AI がどれだけ間違えても損失は設計した範囲に収まる |
| P2 | **権限は実績で渡す** | AI の自己申告の確信度は当てにならない。判断を全件記録して答え合わせし、統計的に基準を満たしたら権限 (承認なし発注・資金量) を広げる (§8) |
| P3 | **中期なので日次バッチで十分** | リアルタイム不要 → LLM 代は月数ドル規模 |
| P4 | **安いモデルは「数」と「検証」で補う** | 異系統モデルの多数決 + 原文照合 + 事実の読み取りチェック。1回の高価な呼び出しより安く、誤りに強い |
| P5 | **LLM を使う前に、使わずに済ませる** | 重複除去・銘柄辞書マッチ・キャッシュで大半の文書は LLM に渡さない |
| P6 | **迷ったら何もしない (fail-safe)** | 合意なし → 棄権。予算超過・データ欠損・反対役の失敗 → 新規エントリーしない |
| P7 | **すべてを記録し、再現できる** | ワークフローの各ノードの入出力を保存。「その日なぜ買ったか」を後から追え、過去日付で同じ手順を再生できる |

## 2. 全体像 = ワークフロー

処理はすべて **ノード (型付きの入出力ポートを持つ部品) をつないだワークフロー** として YAML で定義する (`workflows/*.yaml`)。

```
 情報                                                    判断 → 制限 → 承認 → 執行
 ┌──────┐  ┌─────┐  ┌──────┐  ┌────────┐  ┌───────┐  ┌──────────┐
 │ news │→│dedup│→│ match│→│extract │→│history│→│eventScore│─┐
 └──────┘  └─────┘  └──────┘  │(LLM合議)│  └───┬───┘  └──────────┘ │  ┌──────┐
                              └────────┘      │                   ├→│score │─┐
 ┌──────┐  ┌───────┐                          │                   │  └──────┘ │
 │prices│→│factors│──────────────────────────┼───────────────────┘           │
 └──┬───┘  └───┬───┘                          ▼                               ▼
    │          │                         ┌──────────┐  ┌───────┐  ┌───────┐  ┌───────┐
    │          └───────────────────────→│ decide   │→│propose│→│approve│→│execute│
    │  ┌───────┐                         │(AI合議)  │  │(リスク│  │(承認  │  │(ペーパ│
    └→│account│────────────────────────→│          │  │ 制限) │  │ ゲート)│  │ ー約定)│
       └───────┘                         └────┬─────┘  └───────┘  └───────┘  └───────┘
                                              ▼
                                         ┌──────┐  ┌──────────┐
                                         │record│→│ scorecard │  確度の答え合わせ
                                         └──────┘  └──────────┘
```

| 実行 | 頻度 |
|------|------|
| 日次ワークフロー (収集 → 判断 → 提案) | 1日1回 (引け後) |
| 本番 AI フローと **ルールのみのベースライン** を並走 | 毎日 (共通ノードはキャッシュされ追加コストほぼゼロ) |
| 採点 (scorecard) | 毎日 (20営業日経過した判断から順に確定) |

## 3. データソース

**公式 API・RSS を優先**。スクレイピングは利用規約・robots.txt を確認したうえで最小限。

| 種類 | 日本株 | 米国株 | 中期シグナルとしての価値 |
|------|--------|--------|--------------------------|
| 価格・出来高 | **J-Quants**（実装済み）, CSV（Stooq は 2026 年から自動取得不可） | **Twelve Data**（実装済み） | ◎ モメンタム/トレンド |
| 財務・業績 | J-Quants, EDINET API | SEC EDGAR | ◎ 業績修正・クオリティ |
| 適時開示 | TDnet | **SEC 8-K・13D**（EDGAR、実装済み） | ◎ 一次情報 |
| インサイダー売買 | — | **SEC Form 4**（EDGAR、実装済み） | ○ 市場での買いは中期の材料 |
| ニュース | Google News RSS, 各社 RSS | Yahoo Finance / Google News の英語 RSS | ○ 裏取り (複数報道) |
| SNS | (規約上の制約大) | Reddit API 等 | △ 単独では使わない |
| マクロ | 日銀, e-Stat | FRED | ○ 地合い判定 |

- 情報源ごとに信頼度の重み (`sourceWeight`)。運用データが溜まったら当たり率でベイズ更新
- **裏取り**: 同じ記事見出しが複数の情報源に出たら (`dedup` が `alsoSeenIn` に記録) ボーナス

## 4. シグナル

### 4.1 定量ファクター (LLM 不要) — `signal.factors`

モメンタム 12-1 / 対ベンチマーク相対強度 (6ヶ月) / トレンド (終値・SMA50・SMA200) / ATR / 60日ボラ。

### 4.2 イベント抽出 (LLM 合議) — `llm.extractEvents`

ニュース・開示 1 件を固定スキーマに変換: `relevant, tickers, eventType(列挙), direction(-2..2), materiality(0..3), horizon, confidence, evidence(原文引用), rationale`。

### 4.3 イベントスコア — `signal.eventScores`

```
score_i = Σ direction × w(materiality) × confidence × 合意率 × 情報源重み × 半減期減衰 × (裏取りボーナス)
```

### 4.4 AI の売買判断 — `decide.ai`

候補銘柄ごとに **事実だけを並べた資料 (dossier)** を作り、安価モデル群に「今後20営業日でベンチマークに勝つか」を判断させる。

```
出力: stance (bullish / neutral / bearish / abstain), conviction, checklist{trend, news},
      thesis, invalidation (撤回条件), evidence (資料からの引用)
```

| 確度を上げる仕組み | 内容 |
|-----|------|
| **棄権を許す** | 判断できなければ `abstain`。モデル間で合意しなければ自動的に `abstain` (P6) |
| **事実の読み取りチェック** | `checklist.trend` / `checklist.news` が資料の事実と一致しない票は棄却 (読み間違い・幻覚を機械的に検出) |
| **根拠の原文照合** | `evidence` が資料に実在しない票は棄却 |
| **撤回条件の必須化** | bullish / bearish には撤回条件が必要。書けない判断は棄却 |
| **反対役 (レッドチーム)** | 買い合意に対し別モデルが「買うべきでない理由」を資料から探す。根拠付きで重大な理由があれば拒否 (veto)。反対役自体が失敗したら拒否 (fail-safe)。「買う」より「止める」を簡単にする非対称設計 |
| **保守的な統合** | 合意グループ内で conviction は最小値を採る |

比較用に同じ入出力の `decide.rules` (スコア上位 N を bullish) を用意し、毎日並走させる。

## 5. LLM ハーネス (`packages/core/src/harness/`)

| # | 仕組み | 防ぐもの |
|---|--------|---------|
| H1 | 構造化出力 + Zod スキーマ検証 + エラー内容を添えた再試行 | 形式崩れ・範囲外の値 |
| H2 | 根拠の原文照合 (NFKC 正規化・空白/引用符/省略記号を無視、ほぼ一致を許容) | 幻覚 |
| H3 | 異系統アンサンブル: 逐次投票、quorum 到達で打ち切り、重要案件のみ上位モデルが仲裁 (安いモデルの1つと一致必須) | 単一モデルの癖・ブレ |
| H4 | コンテンツハッシュキャッシュ (モデル × プロンプト版 × 入力) | 重複コスト |
| H5 | 日次予算上限 (未登録モデルは悲観的な単価で計上) | コスト暴走 |
| H6 | 判断の全件記録と採点 (§8) | 気づかない劣化 |
| H7 | 事実の読み取りチェック (§4.4) | 読み間違い |
| H8 | 反対役による拒否 (§4.4) | 楽観バイアス |

コスト階層: Tier0 ルール (0円) → Tier1 安価モデル×2〜3 (ほぼ全件) → Tier2 中位モデル (割れた重要案件のみ)。

## 6. リスク制限と執行 (決定論的)

AI がどの銘柄を選んでも、以下は必ず適用される (`portfolio.propose`, `strategy/risk.ts`)。

| 制限 | 既定値 |
|------|--------|
| 1トレードのリスク | 口座資産の 0.75% (= ATR×2.5 の損切りに掛かった時の損失) |
| 1銘柄上限 / 業種上限 / 最大保有数 | 10〜15% / 30〜35% / 6〜12 |
| 損切り | 建値 − 2.5×ATR と 高値 − 3×ATR (トレーリング) の高い方 |
| 時間切れ | 60営業日で含み益なし → 売り |
| 地合いフィルタ | ベンチマークが下降トレンドなら新規エントリー停止 |
| **キルスイッチ** | ドローダウン −15% で新規停止、−25% で縮小 |
| 単元 | 日本株は 100 株単位 |
| 売り | AI が保有銘柄を bearish と判断 → 売り。neutral/abstain なら保有継続 (無駄な回転を避ける) |

執行: `gate.approval` (人の承認ゲート) → 次のいずれか

- `broker.paper`: ローカルの疑似約定 (終値±スリッページ、手数料、現金は整数の最小通貨単位、同一 run で二重約定しない)
- `broker.webull`: **ウィブル証券** に DAY 指値注文。既定 (`trading: dry_run`) は Webull の注文プレビューのみ。詳細は [webull.md](webull.md)
- `broker.ibkr`: **Interactive Brokers** に DAY 指値注文。TWS API で常駐の IB Gateway に接続。口座とモードの照合、本番の三重ロック、呼値への丸め、空売り禁止、金額・件数上限、1日1注文の冪等性 (orderRef) を強制。詳細は [ibkr.md](ibkr.md)

ブローカー選定の経緯は [research/brokers.md](research/brokers.md)。

## 7. ワークフローエンジン (`packages/core/src/workflow/`)

| 機能 | 内容 |
|------|------|
| 型付きポート | ノードは入出力の型 (Documents, Events, Prices, Factors, Judgments, Proposals …) を宣言。YAML 読み込み時に接続の型不一致・必須入力の未接続・循環を検出。ノード実装は TypeScript の型で検査される |
| ノードキャッシュ | `inputs` (入力と設定の純関数) / `daily` (+実行日) / `none` (副作用あり)。AI フローとルールフローの共通部分は1回しか実行されない |
| 失敗時の方針 | ノードごとに `abort` (停止) / `skip` (依存先だけ飛ばす) / `fallback` (安全な既定値 = シグナルなし) |
| 承認待ち | `WaitingForInput` で一時停止 → `approve` → `resume`。完了済みノードは再実行しない |
| 過去日付の再生 | `--as-of` / `--from --to`。各ノードは `now` (再生時はその日の終わり) 以前の情報しか使わない。RSS など過去を再現できないソースは再生を拒否 |
| 記録 | 全ノードの入出力を内容アドレス方式で保存 (JSON 限定: NaN や Date は拒否して往復の正確さを保証)。イベントログ (UI のライブ表示用) |
| グラフ出力 | `stockai graph` で ノード・ポート・エッジ・座標の JSON を出す (ノード UI 用) |

## 8. 確度の計測と権限委譲

### 8.1 なぜ「判断」単位で測るか

中期売買は年数十トレード。勝率 55% を偶然でないと示すには数百トレード = 数年かかる。そこで **毎日・全候補の判断 (bullish/bearish)** を記録し (`eval.record`)、20営業日後の対ベンチマーク超過リターンで採点する (`eval.scorecard`)。

### 8.2 採点項目

| 項目 | 意味 |
|------|------|
| coverage | 方向性のある判断の割合 (棄権が多いほど低い) |
| hit / hit(eff) | 的中率 / 重なりのない標本での的中率 |
| nEff | 20営業日以上離れた判断だけを数えた **実効標本数** (毎日の判断は期間が重なり独立でないため) |
| wilson↓ | hit(eff) の 95% Wilson 下限 |
| excess bull / bear | 判断ごとの平均超過リターン |
| conviction 別的中率 | 確信度が当たりやすさと対応しているか (キャリブレーション) |

### 8.3 昇格ルール (既定)

`nEff ≥ 100` かつ `wilson↓ > 0.5` かつ **ルールのみのベースラインより的中率が高い** → `eligible`。

### 8.4 権限の段階

| 段階 | 承認ゲート | 口座 |
|------|-----------|------|
| 1 記録のみ / ローカル疑似口座 | auto | `broker.paper` |
| 2 **IBKR ペーパー口座** | manual → auto | IBKR ペーパー (本物の約定ルール) |
| 3 少額実運用 | **manual** (人が承認) | IBKR 本番・少額 |
| 4 拡大 | auto (上限付き) | 段階的に増額 |

段階を進める条件は §8.3 を満たし続けること。基準を割ったら一段戻す。

## 10. 技術スタックと UI

| 層 | 選定 |
|----|------|
| 言語 | TypeScript (strict, `noUncheckedIndexedAccess` 等) |
| 実行環境 | Node.js 22 (型ストリップで .ts を直接実行)。**aqua で v22.23.4 に固定**（`aqua.yaml` + チェックサム）、`.npmrc` の engine-strict で不一致を拒否 |
| 検証 | Zod (LLM 出力・設定・ワークフロー定義。LLM に渡す JSON Schema も同じ定義から生成) |
| 保存 | SQLite (`node:sqlite`) |
| テスト | Vitest |
| 構成 | npm workspaces: `packages/core` (エンジン・ハーネス・ノード・CLI)、`apps/web` (後続) |

**UI** (`apps/web`):

1. **ターミナル風の Web 画面（実装済み）**: 等幅（JetBrains Mono + M PLUS 1 Code）、1ch × 1lh のグリッド、アクセント色は1つ、状態は必ず記号 + 色の両方で示す、キーボード操作、ink / paper の2テーマ、値動きの色は日本式（上昇 = 赤）が既定
2. **ノードエディタ（実装済み v0.5）**: 型付きポート同士だけを接続でき、循環はその場で拒否。パラメータ欄はノード定義の JSON Schema から自動生成。編集のたびにサーバーで検証。保存は 1ノード1行の YAML（`stringifyWorkflow`、読み戻して同一になることをテストで保証）。編集画面から実行し、ノードの状態をライブ表示

| 層 | 選定 |
|----|------|
| API サーバー | `node:http`（依存なし）。JSON API、SSE でライブ更新、実行キュー（1件ずつ）、日次スケジューラ |
| 画面 | React 19 + Vite。素の CSS（デザイントークンは CSS 変数） |
| 安全 | 既定は `127.0.0.1` のみ。外部公開はトークン必須。POST は JSON のみ（他サイトからのフォーム送信を防ぐ）。承認は2回押しで確定 |
